# CPU 过载专项优化实施记录

日期：2026-11-23
项目：选品工具 0.4.4 发布前性能优化
范围：本地代码和数据库迁移设计；本次没有连接或修改生产服务器。

## 本次已实施

### 1. 上架日期改为持久化字段

- `Product` 新增 `listingDate`，映射数据库字段 `商品主表.上架日期`。
- 增加上架日期 B-tree 索引。
- 迁移按当前公式一次性回填：
  `2026-07-29 + ROUND((商品ID - 1070000000000) / 278550000)`。
- 新商品导入时写入该字段；已有商品只有在字段为空时补齐。
- 商品列表和团队收藏列表直接通过 Product 关联条件过滤日期，不再先查询大批商品 ID 再使用 `IN`。

### 2. 连续上榜改为周期统计关系

新增 `商品周期连续上榜统计表`，唯一键为商品 ID + 榜单类型 + 周开始日期。

- 每条记录保存“以该周为终点”的连续上榜周数。
- 迁移从现有历史表去重后，按连续周分段计算并回填。
- 每次榜单导入后，只重算本批次涉及的商品和榜单类型。
- 商品列表通过 Prisma 关系 `periodStreaks.some` 过滤，不再把所有匹配商品 ID 返回 Node.js。
- 同一商品同一周存在多个类目时，只按一个周期记录计算连续周数。

### 3. 二级类目筛选

改为直接使用商品榜单统计表的 `latestCategoryLevel2`。该字段由导入统计逻辑按“真实二级类目优先、导出时间优先”等既有规则维护，取消额外查询商品 ID 的步骤。

### 4. 列表统计与并发保护

- 商品列表先执行分页查询，再执行 count，避免两条完整过滤查询同时争抢 CPU。
- count 按完整筛选条件缓存 15 秒，最多保留 256 个筛选键；相同筛选条件的并发 count 共用同一个 Promise。
- 商品列表和团队收藏列表共用并发闸门：最多 2 条重查询同时执行。
- 等待队列上限 40；排队超过 15 秒返回 503 提示。
- 执行时间或排队时间超过 1 秒时记录不含用户数据的性能日志。

### 5. Prisma 连接池

Linux 部署脚本生成的 `DATABASE_URL` 增加默认参数：

- `connection_limit=5`
- `pool_timeout=10`

可通过部署环境中的 `POSTGRES_CONNECTION_LIMIT` 和 `POSTGRES_POOL_TIMEOUT` 覆盖默认值。

## 数据库迁移与发布注意事项

迁移目录：`prisma/migrations/20261123100000_product_listing_date_and_period_streaks`

该迁移是增量迁移，不删除旧字段或旧表，但会执行：

1. 为商品主表增加上架日期列并回填现有商品。
2. 创建周期连续上榜统计表和索引。
3. 扫描现有商品上榜历史，生成每个商品、榜单、周期的连续周数。

**生产执行前要求：**

- 先备份 PostgreSQL。
- 建议选择业务低峰执行；商品主表会执行一次批量回填，历史表会被完整扫描并写入周期统计表，可能带来明显的 CPU、IO 和行级锁压力。
- 部署脚本会执行 `prisma migrate deploy`；迁移完成后再启动新 API。
- 本次没有在生产库运行迁移，也没有执行生产压测。

## 回滚策略

本次数据库变更为新增字段、索引和表。若新版本上线出现问题，优先回滚应用代码到上一版本，暂时保留新增数据库结构，不要直接删除字段或表。

如果旧版本运行期间又导入了榜单数据，旧版本不会维护新的周期统计表。再次启用新版本前，需要重新全量重建 `商品周期连续上榜统计表`，不能只依赖本次增量导入逻辑。

## 第二阶段：Keyset 分页与最近 12 周历史 SQL

### 6. 商品列表 Keyset Cursor 分页

活跃的 `/products` 和 `/products/team-favorites` 接口已切换到 Keyset：

- 按当前排序字段建立游标，并统一追加 `productId ASC` 作为唯一稳定尾键，避免同值商品跨页重复或遗漏。
- 支持现有排序字段：最近上榜日期、行业排名、历史上榜周数、连续上榜周数、商品名称、最新支付买家数中值。
- 对可空排序字段明确处理 NULL 顺序；支付买家数中值保持 `NULLS LAST`。
- 游标绑定榜单类型、排序字段/方向和筛选条件 SHA-256；筛选条件变化或游标损坏会返回 400，要求从第一页重新查询。
- 每次只取 `pageSize + 1` 条，用额外一条判断是否存在下一页；响应保留 `page/pageSize/total/totalPages`，并新增 `hasPreviousPage/hasNextPage/nextCursor`。
- 活跃列表查询不再使用 OFFSET；请求第 2 页及以后必须携带有效游标。旧客户端若直接传 page=2 而没有 cursor，会收到刷新列表提示。

前端仍保留上一页/下一页、总页数展示和 50/100 条每页切换。由于纯 Keyset 无法在没有前置游标的情况下直接跳到任意第 N 页，原来的任意页码跳转改为顺序翻页；前端在内存中保存已访问页的游标，上一页可直接返回，不需要重新扫描前面所有页。

### 7. 最近 12 周商品趋势历史改为 PostgreSQL 计算

商品列表和管理员成员收藏列表统一调用参数化 `$queryRaw`：

1. 第一层 `ROW_NUMBER()` 按商品 ID + 周开始日期分组，复刻原有优先规则：真实二级类目优先、导出时间倒序、导入时间倒序、类目名称升序。
2. 第二层 `ROW_NUMBER()` 按商品 ID 分组，按周开始日期倒序，只保留每个商品最近 12 个不同周。
3. 最终结果按商品 ID、周开始日期正序返回，保持趋势图原有时间顺序和数据结构。

Node.js 不再接收整页商品的全部历史记录，也不再执行全量排序、去重和 `slice(-12)`；只负责把数据库返回的最多 12 周数据组装为原有 `buyerTrend`。

本轮无需新增数据库迁移：现有历史表唯一索引 `(榜单类型, 商品ID, 周开始日期, 类目名称)` 已覆盖新查询的榜单、商品和周期过滤前缀。
